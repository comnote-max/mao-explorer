# 実現性評価（2026-11-18）

## 結論
**技術的には実現可能。価値も十分ある。ただし仕様のまま作ると「ファイラー作り」に工数の大半を取られる。**
価値の核は「Gitを用語ごと隠したGitHubクライアント」であり、そこを先に検証すべき。

## 1. 価値の評価
| 観点 | 評価 |
|---|---|
| 競合 | GitHub Desktop / SourceTree / TortoiseGit はいずれも「Gitを知っている人向け」。用語を完全に置き換え、ファイラーに溶け込ませた製品はほぼ無い |
| 想定ユーザー | 非エンジニアのチーム（デザイナー、ライター、事務、学生）がGitHubで資料・原稿を管理するケース。担当者→責任者の承認フローは業務と相性が良い |
| 差別化の本命 | 「本体へ反映依頼」「依頼ボタン点滅」＝PRレビューを業務の承認フローとして見せる部分 |
| 弱み | 通常ファイラー部分はOS標準と比べて優位性を出しにくい。NAS横断索引検索は既存スマホ版の強みを流用できれば差別化になる |

## 2. 技術的な実現性（項目別）
| 項目 | 難易度 | コメント |
|---|---|---|
| 通常ファイラー（ツリー・一覧・タブ・D&D・右クリック） | 中〜高 | 地味に最大工数。OSごとのショートカット、D&D、ゴミ箱、アイコン、大量ファイル表示の性能 |
| OS標準アプリで開く・プロパティ | 低 | |
| NAS（OSマウント済みSMB） | 低 | OSに任せるなら普通のパス。切断判定だけ注意 |
| OneDrive / Google Drive | 低 | 同期フォルダのパス検出のみ。オンデマンド（クラウドのみ）ファイルの扱いに注意 |
| SQLite索引・オフライン検索 | 中 | スマホ版に同等ロジックあり（切断を削除扱いしない設計も既に実装済み） |
| GitHub OAuth（Device Flow）＋OS資格情報 | 低 | GitHub App推奨（権限を絞れる） |
| 未同期プロジェクトの閲覧 | 低 | Contents API / Trees API。API制限（5000回/時）に注意 |
| 初回同期・同期・保存 | 中 | git2(libgit2)で可。LFS・大きいリポジトリ・認証付きpushの扱いが要検証 |
| 状態表示（青・矢印・赤など） | 中 | git status をファイル単位で高速に出す必要あり。ファイル監視と連動 |
| 権限判定・保護ブランチ判定 | 中 | permissions API ＋ branch protection / rulesets API。**保護設定の読み取りには管理者権限が要る場合がある**→読めないときは「実行して失敗理由を表示」に倒す設計が必要 |
| 反映依頼・点滅通知 | 低〜中 | PR API。ポーリングまたはWebhook不可なので定期取得（ETagで節約） |
| 本体に反映 | 低 | Merge API |
| 競合解決画面 | **高** | テキストは3-way表示で可。**Word/Excel/画像などバイナリは行単位の解決が不可能**→「どちらを採用」の二択が現実的 |

### 最大のリスク
1. **非エンジニアがGitに入れるファイルの性質**：Office文書・画像・PDFが中心になる。差分表示・競合解決が意味を持たず、容量も膨らむ（GitHubは100MB/ファイル上限、LFSは有料枠）。→ 対象をテキスト中心にするか、バイナリ前提の「ファイル単位の上書き選択」設計にする。
2. **「保存」という名前**：エディタの Ctrl+S と混同される。「履歴に保存」「記録」等を検討。
3. **仮想フォルダ＝ブランチ**：切替でフォルダ中身が丸ごと入れ替わる挙動は、普通のフォルダの感覚と違う。外部アプリでファイルを開いたまま切り替えると事故る。→ git worktree で仮想フォルダを**実際に別フォルダとして実体化**する案が有力（本当に「フォルダ」になり、切替時の未保存問題も消える）。
4. **同期の自動化範囲**：pullでの自動マージ・競合を非エンジニアに見せない設計（rebase/fast-forwardのみ、駄目なら要対応）が必要。

## 3. 技術構成への提案（重要）
既存スマホ版 `C:\GitHub\filer_smapho` は **Flutter（`mobile/`）** が開発本体（Swift版は評価版）。
最終的に統合する目標なら、**Tauri+React ではなく Flutter デスクトップ（Windows/macOS）を推奨**。

| 案 | 長所 | 短所 |
|---|---|---|
| A. Tauri 2 + React（仕様書案） | 軽量、Web UI資産、Rustでgit2 | スマホ版と**UI・索引ロジックを二重実装**。統合時に作り直し |
| **B. Flutter Desktop ＋ Rust(git2) を flutter_rust_bridge で接続** | スマホ版の索引・検索・SQLite・画面を共有。最終統合が自然 | デスクトップのD&D・右クリック等はプラグイン頼りで一部手作業 |
| C. Flutter ＋ git CLI 呼び出し | 実装が速い | 利用者PCにgitが必要、モバイルで使えない |

→ **B案を推奨**。Git処理はRustに閉じ込めれば、将来スマホ版（iOS/Android）でも同じGitコアを使える。
※「既存MAO Git Explorerの実装」はC:\GitHub直下には見当たらなかった。別の場所にあれば要確認。

### 3.1 方針更新（2026-11-18）
- Windows/Mac版はOSSで公開する。スマホ版への統合は公開後に検討する最終目標とする。
- これを受けて、**Tauri 2 + React（仕様書案）を採用可**とする。GitとGitHubの処理、索引はRustのcrate（`mao-core`）に分け、将来はflutter_rust_bridgeでスマホ版から再利用する。
- 自作コードのライセンスはMIT/Apache-2.0の二重ライセンスにする。GPL/AGPLのコード（Spacedriveなど）は取り込まない。将来、スマホ版を非公開で作る余地を残すため。
- GitHubログインはDevice Flowにする。クライアントシークレットが不要なので、OSSで公開しても問題ない。

## 4. 進め方の提案（フェーズ順の組み替え）
仕様書は ファイラー→検索→GitHub の順だが、**価値の検証が最後になる**。次の順を提案：

1. **Phase 0（2〜3週間）PoC：GitHub部分だけ** — ログイン、プロジェクト一覧（公開/非公開・未同期灰色）、閲覧、初回同期、保存、同期、仮想フォルダ、反映依頼、本体に反映。画面は最低限の一覧でよい。非エンジニアに触ってもらい「本当に分かるか」を確認。
2. Phase 1：スマホ版の索引・検索コアを共有化し、デスクトップのファイラー画面を構築
3. Phase 2：GitHubをツリーに統合、状態アイコン、権限別ボタン、点滅通知
4. Phase 3：競合解決（テキスト3-way／バイナリ二択）
5. Phase 4：署名・配布（Windows：コード署名証明書、macOS：Developer ID＋公証が必要＝費用・手続きあり）

## 5. 仕様で詰めるべき論点
- 対象ファイルはテキスト中心か、Office/画像も主対象か（設計が大きく変わる）
- 仮想フォルダを worktree（別フォルダ実体）にするか、切替式にするか
- 「保存」の名称
- 依頼の通知はアプリ起動中のみか、OS通知も出すか
- Organization／個人リポジトリのどちらを主対象にするか
- 料金モデル（無料／買い切り／チーム課金）
