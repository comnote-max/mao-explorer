# PoC設計（GitHub部分）

作成：2026-11-18／期間目標：1週間

## 1. 目的
Gitを知らない人でも、次の流れを用語の説明なしで完了できるかを確かめる。
**閲覧 → 同期 → 編集 → 保存 → 本体へ反映依頼（または本体に反映）**

## 2. 範囲
| 含める | 含めない（PoC後に回す） |
|---|---|
| GitHubログイン（Device Flow）、トークンはOSの資格情報に保存 | 通常ファイラーの作り込み（D&D、タブ、ショートカット） |
| プロジェクト一覧（公開／非公開、同期済み／未同期は灰色） | NAS、OneDrive、Google Drive、索引検索 |
| 未同期プロジェクトの閲覧（APIでツリーとREADMEを表示） | 競合解決画面（PoCでは「要対応」と表示し、ファイル名を出すだけ） |
| 初回同期、同期、保存、仮想フォルダの作成 | 依頼の点滅通知（件数表示までは作る） |
| 本体へ反映依頼、依頼一覧、本体に反映、修正依頼 | 署名、インストーラー、自動更新 |
| 権限によるボタンの切り替え、「権限確認中」の表示 | |

## 3. 決めた設計
### 3.1 仮想フォルダは本物のフォルダにする（git worktree）
```
D:\MAO\<プロジェクト名>\
  本体\              ← 既定ブランチ（例：main）
  見積書の修正\       ← 仮想フォルダ（ブランチ mao/見積書の修正）
  .mao\repo.git      ← 共通のGitデータ（隠しフォルダ）
```
- 切り替えはフォルダを開き直すだけ。未保存の変更を持ち越すかどうかを聞く必要がなくなる。
- 外部アプリでファイルを開いたままでも事故にならない。
- 内部のブランチ名は `mao/<表示名>`。日本語の名前は、Gitで使えない文字だけ置き換える。

### 3.2 同期の規則（非エンジニアに競合を見せない）
1. 未保存の変更がある → 「保存してから同期」を案内する。
2. fetchする → fast-forwardできれば取り込む。
3. ローカルにだけ保存がある → pushする。
4. 両方に変更がある → rebaseを試す。競合したら中止し、元の状態に戻して「要対応」にする（**ローカルの変更は一切消さない**）。
5. force pushは絶対に使わない。

### 3.3 本体への反映（すべてGitHub側で実行）
| 状況 | 処理 |
|---|---|
| 権限なし（pushはできる、本体へは書けない） | 仮想フォルダをpush → PRを作成（本文＝依頼メッセージ） |
| fork必須（write権限なし） | PoCでは「このプロジェクトでは依頼を送れません」と表示する（forkはPoC後） |
| 権限あり、保護なし | `POST /repos/{o}/{r}/merges` か、PRを作って即マージ |
| 権限あり、保護あり | PRを作成し、マージを試す。拒否されたら理由（承認待ち・チェック中）を表示する |
| 完了の判定 | APIで本体の先頭コミットにマージ結果が入ったことを確認してから「本体に反映済み」と出す |

保護設定を事前に読めない（管理者権限が要る）ことがあるため、**実行してみて、拒否されたら理由を表示する**方式を基本にする。表示の判定には `GET /repos/{o}/{r}` の `permissions` を使い、可能なら `GET /repos/{o}/{r}/rules/branches/{branch}` も使う。

## 4. 構成
```
mao-explorer-desktop/
  crates/mao-core/        Rust：画面に依存しない処理（将来スマホ版でも使う）
    auth.rs               Device Flow、資格情報の保存（keyring）
    github.rs             octocrab：一覧、権限、ツリー、PR、マージ
    project.rs            初回同期、worktree、状態の判定
    sync.rs               3.2の規則
    review.rs             反映依頼と本体への反映（3.3）
    status.rs             ファイル単位の状態（git2のstatuses）
  src-tauri/              Tauriのコマンド（mao-coreを薄く包むだけ）
  src/                    React + TypeScript
    terms.ts              表示用語の一元管理（内部名→表示名）
    screens/              Login / Projects / Browser / SaveDialog / RequestDialog / Requests
```
主な依存：`git2`（vendored-libgit2, https）、`octocrab`、`keyring`、`tokio`、`serde`。React側は最低限にする（ルーターとUIライブラリは1つずつ）。

### Tauriコマンド（画面とRustの境界）
| コマンド | 戻り値 |
|---|---|
| `login_start` / `login_poll` | 表示するコード、URL／ログイン状態 |
| `list_projects` | 名前、公開／非公開、同期済みか、権限 |
| `browse_remote(project, path)` | APIで取ったツリー |
| `first_sync(project, dest)` | 進捗イベント、完了 |
| `list_folders(project)` | 本体と仮想フォルダ、それぞれの状態 |
| `create_folder(project, name)` | 新しい仮想フォルダのパス |
| `changes(folder)` | 変更ファイルの一覧 |
| `save(folder, message, files)` | コミットID |
| `sync(folder)` | 結果（同期済み／要対応＋理由） |
| `request_merge(folder, message)` | PR番号 |
| `list_requests(project)` | 受信と送信の依頼、件数 |
| `merge(project, request or folder)` | 結果と理由 |

## 5. 状態の判定
| 表示 | 条件 |
|---|---|
| 未同期（灰） | ローカルにworktreeがない |
| ローカル変更あり（青） | worktreeに未保存の差分がある |
| 送受信待ち（矢印） | ahead > 0 または behind > 0（最後のfetch時点） |
| 同期処理中 | 処理キューで実行中 |
| 要対応（赤） | rebaseを中止した、またはpushが拒否された |
| オフライン | fetchに失敗した。最終確認の時刻を併記する |
| 同期済み | 上のどれにも当たらない |
| 本体に反映済み | 仮想フォルダの先頭が本体に含まれている（上とは別の表示） |

## 6. 7日間の計画
| 日 | 作業 | 完了の目安 |
|---|---|---|
| 1 | 雛形作成、Device Flowログイン、資格情報の保存 | 再起動してもログインが残る |
| 2 | プロジェクト一覧、未同期の閲覧（ツリーとREADME） | 非公開リポジトリが鍵付きで並ぶ |
| 3 | 初回同期（clone＋本体のworktree）、変更一覧、保存 | 外部アプリで編集すると青になり、保存すると消える |
| 4 | 同期（3.2）、仮想フォルダの作成 | 2台のPCでの往復、競合時に「要対応」になり変更が残る |
| 5 | 反映依頼の作成、依頼一覧と件数、修正依頼 | 権限のないアカウントから依頼が届く |
| 6 | 本体に反映（直接／依頼から）、権限で表示を切り替え、保護による拒否理由の表示 | 3種類のアカウントで表示が切り替わる |
| 7 | 試験と手直し、Gitを知らない人1〜2名に触ってもらう | 説明なしで依頼まで完了できたか記録する |

## 7. 試験の環境（人の作業が必要）
- **GitHub OAuth App の登録**（Device Flowを有効にする）：開発者アカウントでの登録が必要なので、本人が行う。
- 試験用リポジトリ：保護なし／保護あり（承認1件必須）の2つ。
- 試験用アカウント：管理者、writeのみ（反映権限なしの再現には保護ルールを使う）、閲覧のみ。

## 8. PoCの合格条件
1. 画面に「ブランチ」「コミット」「プルリクエスト」「マージ」が一度も出ない。
2. どの失敗でも、ローカルの変更が失われない（意図的に切断や競合を起こして確認する）。
3. Gitを知らない試験者が、説明なしで依頼の送信まで到達できる。
4. 依頼が責任者の画面に件数付きで表示され、そこから本体に反映できる。
